# 电商套图企划

## 这个 skill 在做什么

把"我有个产品要做电商配图"这种粗糙需求，转换成 3 套差异化、可直接交付给下游生图模型的结构化视觉企划。它是一套 6 模块的 prompt engineering 系统，已经在 `references/system_prompt.md` 里完整定义。

## 什么时候用

只要用户的请求落在这些范围里，立刻调用本 skill：

- 电商主图 / 首图 / 搜索图 / 推荐流图
- 详情页 / 详情图组 / A+ 页面 / 描述图
- 种草图 / 小红书笔记封面 / 笔记内页
- 抖音商品卡 / 抖音封面 / 橱窗承接图 / 直播间背景
- 大促海报 / 活动海报 / 会场图 / 促销图
- 参数图 / 规格图 / 卖点图（独立任务）
- 原稿改版 / 排版优化 / 视觉升级（用户上传"看起来很糟"的成品图）
- 用户单纯说"给这个产品做几张图"、"电商套图"、"产品配图方案"

不要因为用户没说"高级"或没显式提到模板就跳过——本 skill 的价值正在于替用户把模糊需求结构化。

## 怎么用（执行流程）

### Step 1：完整加载系统提示

**先读一次 `references/system_prompt.md`**（约 1370 行，是整套系统的核心），把它作为你后续所有推理的大脑。这一步不能省。

### Step 2：把用户输入对齐到模块一的资产清点

按系统提示中"模块一 studio_orchestrator"的规则，对用户当前轮次的输入做：

- **资产清点**：识别产品图、对标图（视觉防呆筛选——多角度同产品要合并视为产品多视角矩阵；明显的废图打 `[ASSET_REF_FALSE]`）、文本意图。如果用户没给文字，注入兜底文本"基于该产品的物理特征，生成符合电商平台高转化率的基础商业详情图方案"。
- **状态机打标**：判定全局模式（`STYLE_FUSION_MODE` / `FREE_FISSION_MODE` / `STYLE_GUIDED_MODE` / `REDESIGN_MODE`）、`TASK_TYPE`（主图/详情页/种草图/海报/商品卡/参数图/直播背景/UNSET）、`IMAGE_COUNT`（具体数字 / 默认值 / UNSET）。
- **三阶段推理链路**：严格按系统提示中的 phase_1（模块二、三独立预解析）→ phase_2（交叉融合校准）→ phase_3（认知锁定）执行，不可短路。

### Step 3：按模块二、三、四、五、六依次推演

完整走完六个模块，每一步都要严格遵守对应模块定义的规则、禁忌、修正机制。重点：

- **模块二**冲突仲裁：Level_0 > Level_1 > Level_2 > Level_3，硬性约束永远胜出。
- **模块三**：产品 DNA 必须无损保留品牌印记和表面图文。
- **模块四**：必须实例化 4 个专家智能体（操盘手、视觉总监、技术指导、转化心理设计师），按风格锚点状态决定 A/B/C 的发散半径，A/B/C 的目标平台必须一致。
- **模块五**：12 条红线（R1-R12）逐条审查，发现违规生成"修正指令"传给模块六，而不是退回上游。
- **模块六**：先输出 `_system_diagnostic_log`，然后在 `options` 数组中输出 3 个完整方案对象。**JSON 必须以 `{` 起手，以 `}` 结束，禁止 markdown 包裹，禁止前后缀自然语言。**

### Step 4：生成 3 套方案并交给用户选择

Step 4 的目标是让用户最终看到 **A/B/C 三套差异化方案**，并从中选择一套进入 Step 5。这里要区分两种运行环境：

#### A. 前端集成模式（默认，适用于套图企划入口）

如果当前系统有前端方案卡片、按钮或结构化消息承载结果，**不要把"回复继续"暴露给用户**。用户体验必须是：

1. 用户一次提交产品图、可选对标图、平台、任务类型、卖点、人群和数量。
2. 系统内部完成 Step 1-3 的六模块推演，并沉淀共享上下文。
3. 系统可以在后台按 A → B → C staged generation 逐套请求模型，以规避 token 截断。
4. B/C 生成时必须复用第一轮共享上下文、产品 DNA、诊断日志、差异化矩阵和方案骨架，不得重新独立推演。
5. 前端等待并合并 3 套结果，统一展示为 A/B/C 三张可选方案卡片。
6. 用户点击某一套方案后，再进入 Step 5 生成该方案的生图 Prompt。

**前端集成模式的关键约束**：
- 六模块推演（Step 1-3）只执行一次，推演结果必须作为 shared planner context 保留并传递给后续方案。
- A/B/C 的目标平台、任务类型、产品 DNA 必须一致。
- A/B/C 的差异化必须来自美学世界观、场景道具、排版策略、色彩温度、转化侧重；不得只换标题或背景色。
- staged generation 是内部防截断策略，不是用户交互流程。
- 如果某一套生成失败，前端可以展示已生成方案并允许重试失败项，但不得把失败项伪装成完整方案。

#### B. 文件交付模式（仅适用于无前端承载的聊天/CLI 环境）

如果当前运行环境没有前端方案卡片，只能通过聊天或文件交付大 JSON，为避免截断，可以分轮写出 3 份独立方案文件：

1. 第一轮完成 Step 1-3 的全部六模块推演，然后只写方案 A。
2. 第二轮直接取用第一轮上下文，只写方案 B。
3. 第三轮直接取用第一轮上下文，只写方案 C，并给出 3 个文件名 + 各自风格名称。

**文件交付模式的默认输出位置**：如果用户没指定位置，写到 `E:\下载\电商skill\` 下。文件名按用户产品/任务起一个有辨识度的前缀（例如 `knotted-T22-详情页方案`），然后：

- `<前缀>_方案A.json` —— 方案 A
- `<前缀>_方案B.json` —— 方案 B
- `<前缀>_方案C.json` —— 方案 C

**独立方案对象的结构**：

```json
{
  "_system_diagnostic_log": { 三份共享同一份诊断日志 },
  "_option_label": "方案 A - <对应的风格名称>",
  "option": { 这一套方案的全部字段 }
}
```

`_option_label` 字段是给人类看的可读标签，包含 A/B/C 字母和方案的"风格名称"，方便用户一眼辨认这是哪一套。

### Step 5：等用户选定方案后，输出"画面+文字一体化"生图 prompt **Markdown 文件**

Step 1-4 是 skill 的「方案企划」阶段，产出的是方案卡片或策略文档。**当用户挑出 A/B/C 中的某一套**（例如前端点击"选这套生成生图 Prompt"，或聊天中说"用方案 A"、"我选 B"、"展开成 prompt"、"怎么投喂 Nano Banana / GPT-Image"），进入「生图执行」阶段。

#### 用户工作流的硬约束（决定了输出格式）

用户调用生图 API 是**单次调用、一次一张图、无对话上下文**。所以：

- ❌ 不能输出 JSON——找 `full_prompt` 字段还要解析、复制摩擦大
- ❌ 不能依赖"先发 global_briefing 再发每张 prompt"——API 调用没有上下文记忆
- ✅ 必须输出 **Markdown 文件**，每张图一个独立的 ```text``` 代码块（Markdown 渲染器右上角有"复制"按钮，一键复制）
- ✅ 每段 `full_prompt` 必须**完全自包含**：产品 DNA、色彩 HEX、字体、风格 tag、负向词全部内联到这一段里，单独喂给 API 也能正确出图

#### 输出文件

`<前缀>_方案<X>_生图prompt.md`，与方案 JSON 同目录。

#### 关键执行要求

1. **每段代码块完全自包含**：产品材质/颜色/形态、所有色彩 HEX、字体名（中文用 Source Han Sans Heavy / 思源黑体 Heavy 等具体名）、风格 tag、负向词全部内联。下游 API 单次调用无需任何额外信息即可出图。
2. **末尾追加 GLOBAL NEGATIVE 兜底**：每段 prompt 末尾空一行后追加 `GLOBAL NEGATIVE (additional safeguards): ...`，作为整套方案的全局禁忌兜底（在已有的 `Avoid:` 段之外的额外保险）。
3. **TEXT OVERLAY 渲染语法**：在 prompt 中明确写 `TEXT OVERLAY (rendered directly into image, integrated typography, sharp clean text):` 后跟每条文字的内容、位置、字体类别（sans-serif / serif / handwritten）、字重、颜色 HEX、相对字号关系。生图模型靠这种结构化描述才能稳定渲染中文。
4. **区分"产品本体物理文字"与"叠加文字"**：产品 logo、浮雕等物理印记，必须在 prompt 里明确标注 `(this is physical product embossing/printing, not overlay text)`，避免模型把它当成普通可改的文字层。
5. **禁止参数后缀**：绝对不能在 prompt 结尾加 `--ar 1:1 --style raw --v 6 --niji` 这类 Midjourney/SD 后缀。Nano Banana Pro 与 GPT-Image 不识别，只会被当成乱码污染 prompt。比例用自然语言写：`for 1:1 square composition` / `for 3:4 vertical composition`。
6. **图组心理节拍闭环**：N 张图必须覆盖"看见 → 心动 / 兴趣 → 确信 → 决定"四个节拍（确信节拍通常占 2-3 张），在小节标题用 emoji 标注，让用户验证转化逻辑完整。
7. **小节标题格式**：`## <emoji> 图 NN　<标题>`（emoji 与"图"之间一个空格，"NN"用两位数 01-09 保证排序，"图 NN"与标题之间用全角空格分隔）。

#### 实现方式

推荐先在内存里构造一个 prompt 列表（dict 数组），然后用 Python 模板渲染成 Markdown。这样保证 9 段 prompt 的格式严格统一。

#### 验证

写完后用 Python 校验：
- 文件存在且大小合理（通常 20-40 KB）
- 用正则统计 ```` ```text ```` 代码块数量是否等于图片数量
- 抽样打印每张图的标题 + 主标，让用户一眼看到内容骨架

#### 不要做的事

- **不要**输出 JSON 格式的生图 prompt（旧 `_生图prompt.json` 模式已废弃——用户工作流是单次 API 调用，无法解析 JSON 里的字段）。
- **不要**把"加字"作为后期可选步骤推荐——用户已声明走 AI 直出。
- **不要**少于方案约定的图片数量（每张都要补全代码块）。
- **不要**让任何一段 prompt 依赖"前面已经说过"——每段都得自给自足。

## 几条不能踩的红线（核心原则速查）

这些原则在 `system_prompt.md` 里都有完整定义，先记在最上面：

1. **产品参数零幻觉**：用户没说的尺寸、价格、认证、成分、产地，全部填 `"未明确"`。绝对不能编造。
2. **产品 DNA 不可篡改**：磨砂塑料就是磨砂塑料，不要在方案里偷偷改成"拉丝金属"。
3. **A/B/C 平台必须一致**：平台是全局约束不是差异化维度。差异化来自美学世界观、场景道具、排版策略、色彩温度、转化侧重。
4. **物理常识不可违背**：非防水电子产品不能浸泡水里；毛绒玩具不能配大理石冷光。冲突时按"同等情绪价值"做动态材质替换。
5. **沙盒原文一字不改**：用户的奇葩长尾需求（"五彩斑斓的黑"那种）要原样搬运到 `用户需求原文` 字段。
6. **JSON 绝对纯净**：以 `{` 开始、`}` 结束，无 markdown 代码块、无任何前后缀文字。
